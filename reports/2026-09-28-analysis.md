# 로컬 추론 스택 분석 — 2026-09-28

M3 Max(36GB, macOS 26.6.2)에서 세 가지를 측정했다.
- Jev 스타일 결정 모델 두 개
- Qwen3-8B 채팅을 vLLM과 Ollama로 돌렸을 때
- Ollama 병렬 설정

원자료는 `bench/report.md`, `bench/llm_report.md`에 있다.

## 결론

1. **결정 모델은 Ollaya + Laya를 쓴다.** CLM-8B보다 첫 호출 기준 4.6배 빠르고(40ms 대 184ms) 정확도가 높으며(75% 대 40%), 메모리는 약 0.9GB로 CLM의 약 20GB보다 훨씬 적다.
2. **Qwen3-8B 채팅**은 혼자 쓰면 Ollama가 낫다. 4bit끼리 단건 생성 속도가 비슷하고(약 30~45 tok/s), 메모리는 vLLM 예약분의 절반 이하다. 동시 요청이 많다면 vLLM(vllm-metal)이 맞다.
3. **Ollama 병렬값을 올리는 것은 이 맥에서 이득이 없었다.** 병렬 1이 가장 빨랐다. ko-qmd 검색은 Ollama를 쓰지 않으므로, 이 설정을 바꿔도 ko-qmd 속도는 달라지지 않는다.

## 1. 결정 모델: CLM vs Laya

30문항 × 3회를 순차로 돌렸다. 정확도는 동작 확인 수준의 참고값이다.

| 엔진 | cold | 첫 호출 p50 | 정확도 | 메모리 |
|---|---|---|---|---|
| CLM-8B (vllm-metal bf16 인코더) | 4303ms | 184ms | 126/315 (40%) | 약 20GB |
| Ollaya `laya:en` (MLX, F32) | 499ms | 40ms | 237/315 (75%) | 약 0.9GB |

- vllm-metal 인코더는 제대로 동작한다. 같은 문장 4개에 대해 transformers(MPS, bf16, last-token, L2 정규화)로 뽑은 임베딩과 cosine이 0.99985~0.99999로 일치했다.
- CLM은 README 예제의 department(0.987)와 frustration(2.00)은 재현했지만, urgency는 0.852가 나와 README 값 0.41과 크게 다르다. 원인은 찾지 못했다. 같은 티켓에 Laya는 urgency 0.795를 냈다.
- CLM은 이 질문셋에서 답이 한쪽으로 쏠렸다. frustration은 거의 항상 2.0이었고, department는 billing으로 몰렸다. CLM이 강점으로 내세우는 영역은 에이전트 검증 벤치마크라서, 이번 고객 문의 분류 과제와는 결이 다르다.

## 2. Qwen3-8B 채팅: vllm-metal vs Ollama

조건: 프롬프트 8개, 최대 256토큰, temperature 0, thinking 끔. "동시"는 8개 요청을 한꺼번에 보낸 경우다.

| 서버 | TTFT p50 | 단건 생성 속도 | 동시 8건 합계 | 메모리 |
|---|---|---|---|---|
| vllm-metal bf16 | 197ms | 16.8 tok/s | **77.3 tok/s** | 약 20GB 예약 |
| vllm-metal MLX 4bit | 291ms | 30.2 tok/s | 48.6 tok/s | 약 20GB 예약 |
| Ollama 앱 기본값 (Q4, ctx 32K) | 233ms | 29.4 tok/s | 30.2 tok/s | 10GB |

- 동시 요청을 묶어서 처리(batching)하는 것은 vLLM뿐이다. 다만 vLLM에서는 4bit가 bf16보다 동시 처리 성능이 낮았다.
- Ollama의 OpenAI 호환 API는 `/no_think`와 `think:false`를 무시한다. `reasoning_effort: "none"`을 보내야 thinking이 꺼진다. 이걸 넣지 않은 첫 측정은 thinking 토큰이 max_tokens를 다 써 버려서 폐기했다.

## 3. Ollama 병렬 설정

Ollama 앱은 기본값 `OLLAMA_NUM_PARALLEL=1`, 컨텍스트 32K로 떠 있었다(서버 로그 `n_seq_max = 1`). 앱은 건드리지 않고 11436 포트에 별도로 `ollama serve`를 띄워 측정했다. 컨텍스트는 vLLM과 같은 4096으로 맞췄다.

| 설정 | TTFT p50 | 단건 생성 속도 | 동시 8건 합계 | 로드 크기 |
|---|---|---|---|---|
| parallel 1, ctx 4K | 134ms | **45.3 tok/s** | **40.7 tok/s** | 5.9GB |
| parallel 4, ctx 4K | 163ms | 37.3 tok/s | 17.5 tok/s | 7.8GB |
| parallel 8, ctx 4K | 596ms | 7.8 tok/s | 8.9 tok/s | 10GB |

- **병렬값을 올릴수록 느려졌다.** 동시 처리 합계뿐 아니라 요청을 하나씩 보낼 때의 단건 속도도 떨어졌다. 슬롯 수만큼 KV 캐시가 커지면서 flash attention이 꺼진 상태의 연산 비용이 커진 것으로 추정한다(미검증).
- **컨텍스트를 32K에서 4K로 줄인 것만으로** 단건 속도가 29.4에서 45.3 tok/s로 올랐고, 메모리도 10GB에서 5.9GB로 줄었다. 두 측정 사이에 다른 조건이 섞였을 수 있어 효과 크기는 미검증이다.
- **flash attention을 켠 측정은 폐기했다.** 측정 도중 ko-qmd의 `bench-vault-paraphrase.ts`가 Ollama 앱(qwen3:4b)으로 돌기 시작해 GPU를 나눠 썼다(12:24 시작). goldset 확대 생성 작업으로, 문서 약 285개를 하나씩 처리하며 23:30 KST쯤 끝날 예정이다(ko-qmd 세션 추정, 미측정). 이어받기 기능이 없어서 중간에 멈추면 진행분이 전부 날아간다. 재측정은 이 작업이 끝난 뒤 한다.

### ko-qmd와의 관계 (ko-qmd 세션 답변, 2026-09-28)

- ko-qmd 검색(embed, rerank, query expansion)은 node-llama-cpp가 GGUF를 프로세스 안에서 직접 돌린다. Ollama로 HTTP 요청을 보내지 않는다.
- Ollama를 쓰는 곳은 오프라인 데이터 생성 스크립트 두 개뿐이다: `bench-vault-paraphrase.ts`(`ollama run qwen3:4b`)와 `bench-vault-summarize.ts`(`/api/generate`, gemma3). 둘 다 요청을 한 번에 하나씩 보낸다. paraphrase는 오늘 goldset 확대 작업으로 다시 돌고 있다.
- 따라서 `OLLAMA_NUM_PARALLEL`을 올려도 ko-qmd에는 이득이 없다. 생성 스크립트가 병렬 요청을 보내도록 바꾸지 않는 한 효과가 없다.

## 권장

- Ollama 앱에는 `OLLAMA_CONTEXT_LENGTH=4096`(또는 실제로 쓰는 길이)만 걸고, 병렬값은 1로 둔다. 적용하려면 앱을 재시작해야 하고, 효과 크기는 재측정으로 확인해야 한다.
- 결정 판단은 Ollaya + Laya를 쓴다. vllm-metal은 동시 요청을 받는 서빙이나 임베딩을 정밀하게 제어해야 할 때만 띄운다. 띄우면 약 20GB를 예약한다.

## 한계

- 모든 수치는 각 조합을 한 번씩 돌린 결과다. 프롬프트는 8개, 질문은 30문항이다.
- 측정하는 동안 브라우저(Whale) 렌더러가 CPU를 약 200% 쓰고 있었다.
- flash attention 측정과 컨텍스트 길이 효과는 재측정이 필요하다.

## 4. Laya 한국어 정확도 (추가 측정)

같은 30문항(총 105개 판단)을 한국어로 옮긴 `bench/questions_ko.jsonl`로 측정했다. 한 번씩만 돌렸다. 측정하는 동안 ko-qmd의 생성 작업이 Ollama 앱에서 돌고 있었기 때문에, 지연 시간은 참고용이고 비교할 값은 정확도뿐이다.

| 모델 | 한국어 | 영어 | 한국어 약점 |
|---|---|---|---|
| `laya:multilingual` (683MB) | **69/105 (66%)** | 79/105 (75%) | frustration 2/15, tone 7/15, topic 8/15 |
| `laya:en` (853MB) | 35/105 (33%) | 79/105 (75%) | 거의 모든 항목 |

- 한국어 입력에는 `laya:multilingual`을 써야 한다. `laya:en`은 한국어에서 정답률이 33%로 떨어진다.
- multilingual도 한국어에서 영어보다 9%p 낮다. 부서 분류, 긴급도, 환불, 스팸은 한국어에서도 12~14/15로 잘 맞혔다. 반면 감정·어조 계열(frustration, tone)과 topic은 약했다.
- 영어에서는 두 모델의 정확도가 같았다(75%).
- 지연 시간은 multilingual이 한국어 p50 61ms, 영어 p50 45ms였다. GPU를 나눠 쓰는 상태에서 잰 값이다.
